- **Windows targets build images that run**: `jac build --native --target-triple x86_64-pc-windows-msvc` wrote a well-formed PE image that failed to load, because it imported pthread keys, `printf`, the standard streams and `setjmp` from `msvcrt.dll`, and nothing that touched a file, a directory or the clock built at all. A Windows image now stands on a floor: link glue that gives the native runtime the C library it was written against, over the Universal C Runtime (`ucrtbase.dll`) and `kernel32`, with the meaning and record layouts those names have on Linux. It covers the printf family, files and `stat`, directory listing, `rename` that replaces, `realpath`, the environment and the current user, clocks and sleeps, threads and thread-local storage, and `dlopen`; strings are UTF-8 throughout. Records cross to C functions by the Microsoft x64 convention, `hashlib` and `hmac` use the system's CNG instead of OpenSSL, and the PE linker links objects with more than 65,534 relocations. Building needs no C toolchain and works from Linux or macOS. A C library a program names (`import from mylib { ... }`) is imported from `mylib.dll` beside the executable. Not yet on Windows: `socket`, `subprocess`, `signal`, `sqlite3`, `ssl`, and Windows path semantics in `os.path` (drive letters and backslashes; forward-slash paths work).
