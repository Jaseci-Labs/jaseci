- **Fix: a C record can embed a C record declared in another module**: a native `import from <lib> { obj ... }` record with a field typed by a C record that another Jac module declares failed with `E5092: Native lowering failed for type`, because a unit laid out its own records before those of the modules it imports. The embedded record is now laid out on demand. On the Python side the same module raised `NameError: C type '...' is not bound` as it loaded, because the import of the embedded record was dropped as unused there; an import that a kept C block's declarations are typed by now stays with the block. Calling a C function from the Python side of a module that binds a system library by its bare name (`import from c { ... }`) also failed on Linux with `cannot load C library: ... invalid ELF header`, because glibc's `libc.so` is a linker script and not the library; the binding now asks the system which file the name means when the plain file name does not load. A record imported under another name (`import from a { Inner as Held }`) is bound on the Python side too: the block's descriptor now names a field's or parameter's C type the way the module spells it. A module that only declares the record (nothing on its own Python side names it) keeps the block bound there as well, so importing the record from it no longer fails with `cannot import name`.
